## 1. 建议作为白皮书出发点的论点

**使用者贡献了真实使用经验，也应有办法共同看见 AI 的能力边界。**

模型平台能够观察大量服务内交互，而使用者、创业者和研究者往往只能获得产品发布、公开评测和零散案例。平台观察到的情况也不是全部现实：一次对话是否最终解决工作、用户是否依靠人工修复、输出是否被实际采用，都可能超出平台的可见范围。因此，项目希望缓解的是双方各有盲区、且观察能力不对等造成的信息差。

当模型或平台把某类任务纳入通用能力，围绕该任务建立的创业产品可能面临差异化压缩。我们希望把这种变化拆解为可以核对的问题：新增了什么能力，在什么条件下可用，实际完成质量如何，人工参与多少，成本怎样变化，以及是否出现可观察的用户迁移。功能重叠、商业压力与公司倒闭是不同结论。

这些问题需要共同维护的公共证据。项目的建议定位是：**由人和 Agent 共同贡献、以隐私保护为前提、允许独立复核的 AI 能力公共记录。** 新闻、任务方案、执行报告、Challenge 和进度估计都从这份记录生长出来。

## 2. 可以直接进入白皮书的正文草案

> AI 正在改变人们完成工作的方式，但理解这种变化所需的信息分散在模型平台、企业与个人的使用过程中。社会需要持续、可追溯、允许质疑的公共证据，才能判断 AI 已经完成什么、仍然做不到什么，以及能力变化可能如何影响工作与创业。
>
> 我们希望让使用者及其 Agent 成为这份公共记录的贡献者。在明确授权和隐私保护的前提下，Agent 可以整理任务条件、执行结果、人工参与和可公开的验证材料。经过核验、复现和版本化发布，这些分散经验可以形成跨模型、跨工具、跨任务的共同知识。公开方法与修订过程，让读者能够追问每一个结论的依据；保护贡献者，让分享知识不必以交出完整隐私为代价。

## 3. 原始表述应保留的边界

| 讨论中的判断 | 白皮书建议表述与依据 |
| --- | --- |
| 大模型公司掌握我们的隐私数据 | 云端服务可能处理用户提交的敏感内容；处理、保留、安全分析和训练用途必须分别判断。例如 [OpenAI 数据使用政策](https://openai.com/policies/how-your-data-is-used-to-improve-model-performance/)区分个人服务与企业/API 产品，不能推导为所有用户内容都被用于训练或员工可任意查看。 |
| AI / Agent 的发展被隐藏 | 内部研究、真实使用与失败模式对外可见程度有限；隐私、商业秘密与披露选择可能造成缺口。本次材料不足以证明所有公司都蓄意隐藏全部进展。 |
| 没有公开数据集 | 已有公开数据，例如 [Anthropic Economic Index](https://huggingface.co/datasets/Anthropic/EconomicIndex)。项目要验证并补足的是持续性、跨平台可比性、真实任务验收和可追溯性；不是宣称公共研究从零开始。 |
| 一个模型更新杀死一堆创业公司 | 通用平台能力扩展可能挤压部分创业产品的差异化；具体冲击须另看客户迁移、收入、分发渠道和经营事件。不能由发布公告直接推导倒闭因果。 |

## 4. 谁使用它，贡献者为什么参与

| 使用者 | 需要得到的结果 | 可能的贡献动机，待验证 |
| --- | --- | --- |
| 普通使用者与专业工作者 | 判断某种任务能否交给 AI、需要多少检查与人工介入 | 得到可复用方案、减少重复试错 |
| 创业者与产品团队 | 追踪通用能力与自身产品的交集、剩余价值和新需求 | 展示真实能力、获得同行复现与有依据的反馈 |
| Agent 开发者与操作者 | 比较具体环境、版本、成本和验收条件下的表现 | 复用方法、获得署名与验证记录 |
| 研究者、媒体及公众观察者 | 获取可下载、可溯源、可质疑的证据与历史修订 | 建立可复核分析、补充反证与覆盖缺口 |

上述动机是产品假设。投稿数量不是代表性证据；自愿贡献尤其可能偏向成功案例、技术用户和特定工具。

## 5. Open、上报与审计分别意味着什么

建议链路：**授权选择材料 → 本地隐私检查与预览 → 受控接收 → 验证与复现 → 公开批次 → 质疑、更正与撤回处理。**

- **Open：**公开报告格式、任务分类、判断方法、版本差异、来源索引，以及获得许可的样例和数据集。代码、数据和产物的许可分别声明；公开网页不自动等于开放许可。敏感原始材料默认保留在贡献者控制范围。
- **安全上报：**分享范围可以针对单次任务或用户明确选定的一类任务；原始会话、客户信息、凭证及工作目录不默认上传。若报告整理使用云端模型，应先明确哪些材料会离开设备，并在发送前处理敏感内容。“在本地运行 Skill”本身不保证数据不出设备。
- **结果核验：**把 Agent 自述、产物可检查、确定性验收、第三方复现分别标注；记录模型与工具版本、人工参与、失败、重试和未知项。AI 可以辅助核查，但另一个 AI 的同意不自动构成独立验证。
- **平台过程审计：**读者应能追溯采集范围、去重、排除理由、验证者、利益关系、估计方法及修订。项目首先审计自己的证据与发布过程；没有内部访问权限时，不声称审计了模型公司的全部训练数据或内部系统。
- **更正和隐私：**公开结论与方法保留修订记录；敏感材料须有更正、删除与撤回公开展示的处理机制。公开副本可能被第三方保存，不能承诺撤回会消除互联网中的所有副本。

签名或哈希可以帮助发现材料被改动，不能证明报告内容真实、任务成功或提交者独立。首阶段可以使用普通版本化存储和公开修订记录，无需先建设链上系统。

没有观测到进展不等于没有进展；公开任务成功不等于整个职业可被替代。跨平台公开记录可以补充外部观察，不能揭示尚未对外提供的模型内部能力。

## 6. 历史命名探索（已被最终决定取代）

**最终决定：openaiwill / openaiwill.com。** 用户在比较名字的英语语感、开放性和传播关联后明确选择该名称并购入域名。下文保存此前候选分析，不再代表当前推荐或待定事项。

名称应能容纳公开证据、真实任务、进度变化和共同核验。AgentHowTo 容易让人首先联想到教程；WillAI 更像一个对未来的提问。新名称可以把“证据”和“前沿”放在主位，产品副标题解释具体用途。

### 初轮候选：EviFront / 见界（未采用）

- 构词：Evidence + Frontier，表达“用证据看见 AI 前沿”；这是本次提出的品牌含义。
- 中文“见界”表达看见能力边界；英文只有 8 个字母，适合数据产品、研究记录和开发者社区。陌生用户需要副标题帮助理解。
- 建议主域名：`evifront.com`；公共资料或社区域名候选：`evifront.org`；AI 品牌候选：`evifront.ai`。
- 中文副标题：**AI 能力的公共证据库。**
- 中文主张：**让 AI 的真实能力，看得见、查得清。**
- 英文副标题：**Open evidence of AI at work.**
