# 模型、基础数据与运行数据的边界

更新：2026-09-12。

本文收拢本次讨论中已明确的边界：本地固定版本的模型与基础目录，未来导入 PostgreSQL 后提供实际服务；指标来自系统可采集或统计的信号，进度是计算结果值。[独立本体入口](../../datasets/ontology/README.md)提供已实现的代码与产物。[一期业务数据库设计](../superpowers/specs/2026-09-12-postgresql-business-schema-design.md)涵盖本地处理的人物、来源账号、事件、指标和进度；其正式迁移、本地合成回归与真实档案试算现已实现，见[运行说明](../development/local-data-pipeline.md)。

## 当前实际状态

- 当前数据系统不包含周报制作和发布工作流。业务数据库只保留对象、证据、指标/进度及其追溯；数据导入完成不表示对外发布。
- 第一期只做本地采集、处理、入库、指标计算和进度计算，不包含 Agent 上报、用户登录或 Key。Better Auth + Google 及用户领 Key 的已确认用途属于后续阶段，不作为一期前置条件。
- 已有本地 JSON Schema、JSONL 草案数据包及校验器；`datasets/platform/releases/v0.0.1/` 已封存。
- 独立本体合同 `ontology/v1.0.0` 提取五类概念、四类关系及全量参考目录，排除权重和运行数据；其 Schema、生成器及校验器独立于旧平台合同。
- 现有包同时包含目录、定义、空事件/观测集合及值为 null 的进度记录，是一份混合快照，不是最终数据库设计。
- 已有本地 PG 接入、34 张业务表及封存保护；全量本体和五批合成材料已入库并完成指标、实验进度及重放验证。[原 SQL 草案](postgresql-business-schema-draft.sql)保留为设计历史，正式实现以 `db/migrations/` 和运行说明为准。真实标准化档案转换已接通，并完成 2,707 条来源及一个完整赛道的[证据审阅试算](real-data-calculation-2026-09-12.md)；自动事件提取与经过校准的正式估计仍未实现。
- 职业/赛道目录及已分配 ID 继续作为整理起点。指标、事件和进度的旧合同需要修订；本文件不改变已封存文件或现有校验器行为。

## 三种内容，各管一件事

| 内容 | 回答的问题 | 本地文件的职责 | PG 的职责 |
| --- | --- | --- | --- |
| 模型定义 | 有什么对象、字段、关系和约束？ | JSON Schema 描述记录格式；配套说明定义关系语义 | 由建表迁移实现存储结构与数据库约束 |
| 基础数据 | 我们具体定义了哪些工作、赛道、职业、标签和指标？ | 版本化目录记录及配置，包含固定 ID、指标口径、权重和已确定的计算规则 | 导入后供查询、关联与计算使用，并保留版本身份 |
| 运行数据 | 实际采集到了什么，这次统计和计算得到了什么？ | 原始材料、处理结果及待上传批次保存在本地 `data/` | 保存可用于服务的事件记录、指标值和进度值，以及其来源和历史 |

“本地”与“数据库”在这里表示职责。PG 本身也可以在本机运行；本地采集仍可以产生运行数据文件。JSON Schema 不会自动建立 PG 表，JSONL 文件名也不要求与物理表一一对应。

## 对象与数值

| 名称 | 含义 | 是否作为独立业务对象 |
| --- | --- | --- |
| 工作、赛道、职业 | 被组织、关联和跟踪的工作范围 | 是，沿用独立 ID |
| 事件 `event` | 一次发生或已宣布将发生的事项，可由多条来源描述 | 是，有独立 ID |
| 标签 `tag` | 给记录分类、筛选和统计使用的标记 | 可独立标识；与 `label_zh_cn` 这样的显示名称字段区分 |
| 指标 `metric` | 可复用的统计定义，例如评论数或某标签下的记录数 | 是，定义及其版本归属这个指标 |
| 指标值 `metric_value` | 一次采集或统计结果，例如某个范围内有 35 条记录 | 数值记录，引用指标、统计范围、时间和输入依据 |
| 进度值 `progress` | 一项工作或赛道在指定视图、时点和方法下计算出的状态值 | 是对象的状态值，不作为与工作、事件并列的业务实体 |

指标值、进度历史等记录可以有记录 ID，以便去重和追溯。拥有记录 ID 不意味着要把它提升为统一业务实体。

`entity` 是统一对象身份的设计选项：模型可以共享 ID 和类型约定；是否另外设置物理 `entity` 总表，应在 PG 映射中根据统一引用和外键约束确定。它不应代替对象的业务定义，也不用于把所有字段值变成实体。

## 指标使用系统实际能取得的信号

当前指标范围包括来源返回的互动计数，以及对已采集记录执行的计数、去重和聚合。例如评论数、转发数、指定标签下的记录数。工作成功率、风险识别召回率等评测数据不作为本阶段必须取得的输入。

指标定义至少明确统计对象、来源范围、筛选条件、时间窗口、聚合方式、单位和缺失值处理。可复用定义可以接受标签和时间窗参数；每次实际使用的参数随数值记录保存。

以下仅为说明例子，不是实际采集结果或已采用的进度公式：

```text
指标定义：指定标签下最近 7 天的记录数，按去重后的记录计数
本次数值：35
本次范围：明确的标签、来源集合、起止时间和采集覆盖

进度计算：读取事件与指标值，应用指定版本的规则
输出：对应工作/赛道的进度值，附时间、方法和输入记录
```

指标值可以汇总多个事件或多条内容，因此不能强制每个值只归属于一个 `event_id`。直接取得的评论数首先归属于具体来源记录；需要事件总量时另定义聚合口径。没采到、未查询和实际零值分别记录。

进度规则与指标统计规则分开。输出保留估计方法和输入，评论数或标签计数本身不是已经测得的工作完成度。真实试算现采用[明确的 AI 判断与加权方法](real-evidence-estimation-pilot-v1.md)，仍无从互动信号直接测得完成度的公式，不以试算结果补出生产基线。

## 下一版产物和迁移顺序

1. **模型定义与基础目录包**：整理实际对象及其字段，保留完整职业/赛道目录和既有 ID，修订指标定义。包内包含运行记录的格式定义，但不把日常运行记录当作基础目录。
2. **PG 存储映射与建表迁移**：明确每个对象或值记录如何落表、哪些字段是外键、如何保留版本与历史。进度值可以有独立存储表；单独建表不改变它作为状态值的业务含义。
3. **目录导入和运行批次导入**：目录导入沿用原 ID；运行批次引用模型、目录及计算方法版本。同一批次重复导入不重复计数或生成重复进度。

模型、目录和统计/进度方法发生变化时按各自规则发新版本。日常新增事件、指标值和进度值产生运行批次及历史记录，不因为这些数值变化而修改模型定义版本。

旧 v0.0.1 保留用于追溯。拆分必填集合或改变字段含义属于破坏性变更，因此独立本体合同使用 `1.0.0`，并明确记录其来源包与哈希；结构版本不代表生产成熟度。当前已有正式迁移、PG 导入器、计算器、独立合成/真实输入格式及已保存档案适配器，见[本地运行说明](../development/local-data-pipeline.md)；原 SQL 草案和旧混合运行合同保留为历史，不覆盖封存包。

采集和数据导入继续遵守 [SECURITY.md](../../SECURITY.md) 的数据与凭据边界。[本地采集与网站发布](../development/local-collection-and-publishing.md)记录的是其他工作流，不为当前数据系统增加周报或发布功能。
