# 真实材料上的 AI 进度试算方法 v1

方法 ID：`real-evidence-review`，版本：`real-evidence-review-1`。用途是本地试算，不初始化网站生产基线。

本方法把三件事分开：采集器记录真实来源及互动快照；数据库执行明确的去重和聚合；AI 阅读具体证据、写出带假设的工作状态判断，程序再按固定关系权重汇总。分值不是从评论、事件数量、采用阶段、榜单名次或用户自述成功率直接换算而来。

## 范围与终点

本次只使用既有本体中的“应用界面与业务开发”：

| 工作节点 | ID 后缀 | 提议权重 |
| --- | --- | ---: |
| 实现网页移动端与桌面界面 | `software-application-code-frontend-code` | 0.4 |
| 开发业务逻辑与服务接口 | `software-application-code-backend-code` | 0.4 |
| 连接外部系统与数据接口 | `software-application-code-integration-code` | 0.2 |

三个 ID 均以 `oaw:market:` 开头。父节点为 `oaw:market:software-application-code`；完整三个子项都参与计算。权重由 AI 提出：界面与业务逻辑并重，集成保留独立份额。它们不是从经济统计、GDP、劳动时长或帖子分布估算的测量值；调整权重须保留新配置及原因。

终点为该节点范围内的主要工作能够由 AI 独立交付。人可以提出目标、提供授权和验收条件；若主要交付依靠人持续代写或逐步纠错，则不视为完整独立能力。现有材料更多涉及网页和有限代码任务，不能自动推广到所有移动端、桌面端或复杂企业系统。

## 判断输入

每个工作判断保存：

- 保守、中央、积极三个数值；未提出判断时保留空值。
- 具体事件 ID、来源采集 ID 及全文内容哈希。
- 判断者、判断时间、材料截止、方法版本和输入版本。
- 为什么可实现部分工作、哪些能力仍依赖人，以及采用的先验、限制和证据缺口。

数值使用 5 分刻度表达粗略判断。数据库允许更高精度以保证汇总和复算，但不表示判断准确到小数。情景区间不是经过校准的统计置信区间。

证据必须是材料截止前最新的可访问采集，内容哈希匹配，并关联到该工作节点下的已审阅事件。关联状态 `accepted` 表示工作相关性被接受，不能代替声明真实性核验。官方账号身份、供应商陈述、采用方确认、匿名用户自述和重复传播分别保留。

审阅时不以文章标题、被删除的正文、营销口号或无法追溯的数字单独支持数值判断。同集团两个账号发布一次产品接入，仍是一个采用；不同账号复制相同经验帖，仍不构成两份独立验证。社区用户报告的历史运行次数只留在其声明里，不回填为本系统验证过的历史事件。

## 计算

对每个情景分别执行：

`赛道进度 = 0.4 × 界面状态 + 0.4 × 业务逻辑状态 + 0.2 × 集成状态`

评论和事件计数仅记录材料规模及讨论情况，不进入上述算式。一个帖子可以关联多个工作，因此三个工作下的帖子数量不能直接相加当作父级的去重总量。

某个子项没有判断时，父级保留空值与未知权重；不能删除该项后重新归一化。此赛道不代表全部软件工作，更不代表全球进度；没有世界分母时不生成全球总分。

## 时间与可复算性

本次输入来自两个**原帖发布时间窗口**，互动值是随后采集时看到的快照。它们不是各周末的历史快照。当前判断是在材料截止之后形成的一次初始试算；不能把两个窗口的帖子量差异写成进度增量，也不回溯捏造上一周的能力基线。

同一输入、配置和引擎版本重复导入复用同一结果。AI 判断本身已冻结为输入；重新计算是复现该判断的加权结果，不意味着重新调用模型必然得到相同判断。新判断、事实修正、方法修改和关系权重修改需要各自可追溯的新版本或批次。

代码实施与运行命令见[本地数据链路](../development/local-data-pipeline.md)。原始材料、完整判断和运行结果都保留在被 Git 忽略的根目录 `data/`。
