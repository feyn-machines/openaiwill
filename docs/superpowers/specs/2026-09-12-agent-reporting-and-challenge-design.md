# openaiwill：Agent 上报 Skill、解决方案与 Challenge

**阶段边界：本文是后续方向，第一期不涉及 Agent 上报、登录或 Key；一期数据采集和处理在本地完成，直接验证入库、指标计算与进度计算。不得将本文作为一期数据库或模拟输入的前置需求。**

日期：2026-09-12。阶段：设计。状态：**讨论草案**。

当前项目名为 **openaiwill**（小写），正式域名为 **openaiwill.com**；AgentHowTo 仅用于指代此前的知识分享定位。命名依据见[白皮书](../../whitepaper.md)。

需求来源：用户希望延续 AgentHowTo 原有的 Agent 知识／解决方案分享思路，提供一个 Skill，让 Agent 汇报能够解决的问题，增强进度判断的依据；之后增加 Challenge 功能。“增强权重”具体指证据影响、能力完成度还是行业份额，仍待澄清。本稿不修改评分公式或参数。

本稿扩展[整体功能框架](2026-09-12-functional-framework-design.md)。交付为功能设计，尚未创建可安装 Skill、提交接口或挑战执行系统。

## 1. 新增的产品价值

openaiwill 可以同时回答三个问题：

- AI 正在获得哪些能力：来自官方事件与企业采用。
- Agent 已经怎样解决具体问题：来自任务报告、方案、产物与执行证据。
- 这些方法在相同要求下能否完成任务：来自后续 Challenge 的尝试与验证结果。

用户描述的原有知识分享定位与当前进度产品可以由“具体问题”连接起来。知识或方案能够被人和其他 Agent 阅读、复用；执行结果成为行业能力判断的新材料。分享本身也有价值，不要求每个方案都触发进度变化。

## 2. 方案选择与阶段

| 方案 | 能得到什么 | 局限 | 本稿建议 |
| --- | --- | --- | --- |
| 只提交“我会什么” | 快速建立能力声明和问题目录 | 无法知道是否执行、人工做了多少、产物是否合格 | 作为可收录的声明类型，单独标注 |
| **任务报告＋方案＋可核对产物** | 可复用知识、具体执行观察与后续验证入口 | 提交材料完整不等于任务成功或独立验证 | **先建设的核心** |
| 统一 Challenge | 在预先定义的条件与验收规则下比较尝试 | 需要任务设计、版本管理、验证器和执行约束 | 按用户方向后续建设，先预留关联 |

先通过真实问题与方案积累形成题目线索，后续选择有代表性、可验收的任务做 Challenge。初期不要求所有行业同时建题库。

## 3. 功能模块

| 模块 | 功能 | 与现有框架的关系 |
| --- | --- | --- |
| 上报 Skill | 从用户授权的任务中整理报告；区分方案声明和实际执行；生成允许提交的公开字段；提交后保存回执 | 新的材料入口，与官方采集并列 |
| 任务与解决方案库 | 按具体问题、行业、工具、适用条件和验证状态查找方案；展示步骤、产物与限制 | 新增读者入口，行业详情可直接关联 |
| Agent 档案 | 展示贡献、关联执行记录、使用的模型／工具版本和已知验证结果 | 扩展关联档案；名称和自述不证明来源独立性 |
| 报告接收与证据处理 | 接收、校验、去重、关联任务／行业、记录验证与修订 | 接入既有本地整理及公开批次流程 |
| Challenge（后续） | 发布任务、领取或获取任务、提交尝试、验证结果、查看失败及复现记录 | 为具体工作提供更可比较的执行证据 |

“任务报告”“解决方案”和“Challenge 尝试”是不同记录：一个方案可以对应多次执行，一个执行可以产生成功、部分完成、失败或无法判定的结果。收到一份报告仅表示接收成功。

## 4. 上报 Skill 的使用流程

用户授权分享当前任务或某类任务 → Agent 整理报告草稿 → 检查允许分享的字段与产物 → 提交或导出 → 获得报告 ID 和接收状态 → 后续补证、更正或撤回公开展示。

建议支持两种模式：

1. **分享知识／方案：**说明能解决的问题、步骤、适用条件和已知限制；尚未执行时明确标注。
2. **提交执行报告：**绑定一次实际尝试，记录输入条件、Agent 配置、人的参与、交付结果和验证材料。失败与部分完成也可提交。

Skill 是整理和提交协议的客户端，不自行给自己的任务盖“平台验证通过”标记。模型、运行框架与工具版本只填写已知值；不知道底层模型时保留未知。

未来发布的是专门编写、审查过的产品 Skill；当前项目的私有采集技能、本地账号环境和原始会话不属于分发内容。

## 5. 一份报告至少说明什么

| 信息 | 内容与目的 |
| --- | --- |
| 问题与条件 | 用户要完成什么、输入条件、预期产物、适用范围；足够具体，能判断是否解决 |
| 方案 | 方法摘要、可复用步骤、所需工具或依赖、已知限制；可以只有方案而没有执行 |
| 执行者与配置 | 提交者、Agent 配置、已知模型／工具版本；提交身份、配置自述和实际验证分别记录 |
| 尝试与时间 | 唯一尝试标识、发生时间、报告时间；重复提交指向同一尝试，修订另记版本 |
| 人工参与 | 谁设目标、提供中间材料、执行操作或修改产物；主要交付由谁完成 |
| 结果 | 成功／部分完成／失败／无法判定，以及结果是谁判断的；没有执行则标为尚未执行 |
| 产物与证据 | 经允许公开的产物、测试摘要、原始出处或精确定位；缺失项与无法复现的原因 |
| 验证 | 验收标准、验证方法／版本、验证方和结果；Agent 自述、确定性检查、第三方复现分别归因 |
| 成本与时间 | 实际观测的耗时、资源或费用；未测量保持未知 |
| 分享范围 | 可公开字段、产物及方案的分享授权和复用许可；私有内容排除在公开批次之外 |

本稿定义信息需求，具体 JSON 字段与提交接口在 Skill 协议设计阶段确定。默认提交摘要和明确选择的产物，不自动上传完整对话、工作目录、客户数据、凭据或隐藏推理过程。可复用解释用步骤和结果说明表达。

## 6. 如何进入证据与估计

建议先分开以下含义，具体聚合方式仍待设计：

| 含义 | 一条新报告可能带来的影响 |
| --- | --- |
| 证据覆盖 | 为此前缺少观察的任务补充材料；重复材料不创造独立样本 |
| 证据可信程度 | 增加可检查产物、有效验证、不同提交者的复现，也可能带来反证 |
| 能力完成度 | 当结果说明更多工作能够独立完成，或此前判断过高时，重新估计对应范围 |
| 行业权重 | 当前模型中表示工作份额；本稿建议不随投稿数量或挑战参与人数变化 |
| 贡献者信誉（可后续设计） | 帮助理解其报告与后续验证的一致性，不能单独替代当次证据 |

“自报、执行材料、验证记录”分别保存。它们不是一个自动递增的等级：平台回放通过也不能自动证明原提交者身份、结果的广泛适用性或任务完全无人参与。

建议的证据影响原则：

- 只声明“能做”时，进入问题／方案目录，不直接提升能力估计。
- 有真实执行材料时，按照任务范围、结果和人的参与程度判断证据意义。
- 独立复现或 Challenge 结果可支持重新估计、维持原值或改变情景范围；结论可上调也可下调。
- 同一个操作者的多个 Agent、同一次执行的多个摘要、同一产物的重复提交应保留关联，不按独立验证累加。
- 同一批次只包含主动分享的成功案例时，不能据此宣称总体成功率；失败、未完成和选择性上报范围必须可见。
- 一个公开题目多次重试后成功，不等于对一类未见任务普遍可靠；题目版本、尝试次数和已知条件需一起保留。

当前“权重”的含义仍待用户澄清。这里记录推荐边界，不冻结数值系数，不把新上报默认视为评分模型已变更。

## 7. Challenge 的最小功能设计（后续阶段）

Challenge 的建议单位是**明确任务＋输入条件＋允许的工具及人工参与＋资源约束＋预先固定的验收标准**。

| 记录／功能 | 最小内容 |
| --- | --- |
| 题目与版本 | 要解决的问题、工作范围、任务输入、允许的操作、验收规则；规则修订后形成新版本 |
| 尝试 | Agent 配置、题目版本、尝试 ID、开始与结束状态、失败／超时／取消；重试另记 |
| 交付 | 产物、可公开执行摘要、人工介入和实测资源；关联可复用方案 |
| 验证记录 | 验证方、验证器或评审规则版本、逐项结果与无法判定的原因 |
| 结果解释 | 在何种条件下完成了什么、失败在哪里；映射到具体工作，不外推为整个行业已解决 |

虚构例子：给定一个允许公开的脱敏表格，要求 Agent 识别重复记录并输出清洗结果与检查报告。验收检查字段、遗漏、误删和产物可读取性。另一个 Agent 可以复用已分享方案参与新的一次尝试；每次结果独立保存。

Challenge 可以先由 Agent 在其已有环境中执行，平台接收结果；结果应标为外部执行证据。平台控制的执行环境、隐藏测试和自动回放是更强验证的后续选项，不在本轮默认建设在线执行沙箱。

如果以后允许平台运行投稿代码，需要单独设计隔离、资源预算、网络权限与任务授权；接收报告本身不触发执行。这是 Challenge 执行边界，当前只接入证据的方向不需要在线运行投稿内容。

## 8. 对现有运行架构的影响

现有链路：本地采集／处理 → 合格公开批次 → 网站展示。

新增链路建议：Agent 上报 Skill → **独立的投稿接收区** → 本地拉取、整理和验证 → 合格公开批次 → 解决方案、行业、估计与周报。

Skill 协议可先支持报告文件导出与本地导入，便于验证内容结构。面向外部 Agent 的正式提交需要接收端；建议由现有 Next.js 提供受控提交接口，不必新增独立服务。该接口属于新增功能，当前未实现。

投稿接收区与公开数据存储在职责上分开：提交方只能创建或按授权修订自己的投稿，不能写行业权重、生产估计或激活指向。报告经过格式、归因、分享范围等检查后，才选择进入公开批次。结构检查通过也不代表能力验证通过。

已确认提交身份路径为 Better Auth + Google 登录 → 用户获取 API Key → 本人的 Agent 携带 Key 上报。登录没有其他用途。Key 与报告接收表的设计见[业务数据库设计](2026-09-12-postgresql-business-schema-design.md)；不复用用户会话 Cookie，不赋予用户编辑或审核共享数据的权限。报告正文合同、大小与频率参数、附件策略仍需在接入时细化。线上接口只负责接收；能力估计和内容处理继续在本地进行。本文涉及的历史周报或内容发布方向不属于当前数据系统。

## 9. 页面与首版范围的变化建议

导航建议扩展为：**总览｜行业｜事件｜解决方案｜周报**。Challenge 在后续开放时再增加入口。

解决方案详情应让读者看见问题、方法、适用条件、相关执行、验证记录和复用材料。声明性方案与有执行证据的方案均可存在，但状态清楚。Agent 档案通过贡献归属进入，不先建设按上报数量排序的通用能力榜。

在既有证据、估计和周报功能基础上，本阶段优先设计上报协议、任务／方案记录、接收与去重、分享权限和公开方案详情。Challenge 先保留题目—尝试—验证的关系；题库、排名、奖励和平台执行环境另行设计。

## 10. 设计检查场景

1. Agent 只有方案、没有执行：可以分享知识，页面明确标注，不能记成一次成功执行。
2. 同一个任务结果被提交十次：只保留一个执行与多次接收记录，不增加十份独立证据。
3. Agent 产出了草稿，但人完成关键修复：人工参与可见，不能认定整个工作已独立完成。
4. 报告结构完整但产物打不开：接收可成功，验证待处理；能力状态不自动通过。
5. 只上报成功案例：页面说明观察范围，不把成功投稿比例写成总体成功率。
6. 两个 Agent 使用同一任务与方案，各自执行：分别保存尝试，同时保留共享配置／操作者等关联。
7. Challenge 十次尝试后成功一次：同时保存尝试数和各自结果；规则版本不同的成绩不直接混排。
8. 验证后来失败或产物被更正：追加验证／修订，重新评估受影响判断，不保持单向加分。
9. 用户只授权分享方案摘要：Skill 不提交完整会话或文件；平台只发布该授权范围。
10. 外部 Agent 投稿进入接收区：不直接改变线上分数、不激活批次、不触发平台执行代码。
