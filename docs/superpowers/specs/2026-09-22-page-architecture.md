# 页面架构

状态：待评审
日期：2026-09-22

---

## 现状

15 个路由，导航里 4 个。**11 个页面是孤儿或半孤儿。**

```
/  /check  /domains  /domains/[slug]  /capabilities  /capabilities/[slug]
/gates  /gates/[slug]  /method  /occupations  /occupations/[code]
/sectors/[id]  /updates  /updates/[id]  /whitepaper
```

多出来的不是页面，是**三套并行的组织方式**互相打架：按研究对象分（能力／闸门）、
按历史原型分（domains）、按读者分（领域／职业）。

---

## 修订：两种聚合，不是一条下钻链

初稿把 22 个职业组叫成「领域」，于是整个站点变成一条 全局→领域→职业 的下钻链。
这是错的。**同一批工作有两种聚合方式，它们是并行的，不是上下级：**

```
                    工作 19,452 项
                    ╱              ╲
        按谁在做                      按服务什么生意
   职业组 23 → 职业 1,016            市场组 40 → 赛道 265
        → 任务 18,838                    → 工作 614
        （数据齐全）                     （骨架，待赛道桥）
```

CLAUDE.md 本来就写着这是「两种浏览视图」。压成一条链之后，
职业只能作为领域的下级出现，**职业自己的聚合就没有位置了**。

两条轴各自三层，结构对称：

| 轴 | 索引（对比） | 中间（组内） | 叶子 |
| --- | --- | --- | --- |
| 职业 | 22 个职业组 | 组内职业（7–107 个） | 一个职业（923 个） |
| 赛道 | 40 个市场组 | 组内赛道 | 一个赛道 |

赛道那条今天还没有数据，但**位置先留出来**，桥建成后直接填，不再动结构。

```

/occupations/g/[id]    一个职业组：组内职业对比

/markets/g/[id]        一个市场组
/markets/[id]          一个赛道                        ← 待赛道桥

/updates               最近发生了什么
/about                 这是什么 + 方法出口
/whitepaper            白皮书全文
/capabilities/[slug]   能力详情，只从上下文进入，无索引
```

今天上线 8 条，赛道桥落地后补 3 条，**结构不变**。

`/occupations/g/[id]` 里的 `g` 段是有意的：O*NET 职业码形如 `23-2011.00`，
不会与静态段相撞，读者也一眼能看出自己在哪一层。

## 删掉 `/updates/[id]`

单条更新我们自己的详情页只多说一句「它证明了什么」，而读者真正要的是原文。
**源头 URL 实测 4588/4588 全部可取**（`https://x.com/...`），所以：

- feed 每行直接给**源头链接**；
- 「证明了什么」那一句放进行内，不值得一个页面；
- 事件的 `source_count` > 1 时列出全部源头。

前提是把 `canonical_url` 加进发布快照——目前没有发布，这是一项数据工作。
**在 URL 进快照之前，这一页不能删**，否则读者既没有详情页也没有源头。

## 逐页内容（顺序即页面顺序）

### `/` 首页

1. 主张
2. **总进度**——100 格 + 一句话
3. **按职业看**——22 组小倍数，点进 `/occupations/g/[id]`；末尾一条「找具体职业 →」通往 `/occupations`
4. **按赛道看**——占位，赛道桥落地后填
5. 一行限定 + 出口

### 四层不是四遍：每层的信息密度不同

| 页面 | 行数 | 每行放什么 | 干什么用 |
| --- | --- | --- | --- |
| `/` | 22 | 方格条 + 数字 | 扫一眼格局 |
| `/occupations` | 923 | 名字 + 数字 | 找到我自己 |
| `/occupations/g/[id]` | 7–107 | 方格条 + 数字 | 在我的组里比 |
| `/occupations/[code]` | 1 | 全部细节 | 我的答案 |

密度递变是这套结构不重复的原因。任意两层放一样的东西，其中一层就该删。

### `/occupations` 找到你的职业

**不是首页那张对比的翻版。** 首页已经有 22 组的小倍数了，再放一遍就是重复页面。

这一页的任务是**找人**：923 个职业按组分段列出，每行只有名字和一个数字。
读者知道自己叫什么，不知道自己属于哪个组，所以需要一条能直接扫到名字的路径。

- 每行：职业名 · 能做完的占比 · 任务数
- 按 22 个组分段，段头可跳
- **不放方格条**：923 条格子带是噪声，而且页面会长到没法用

### `/occupations/g/[id]` 一个职业组

1. 这个组的数字 + 与中位对比
2. 100 格
3. **时间线**——推动它的更新
4. **AI 在这里做什么**——能力清单
5. **组内职业**——小倍数，点进职业

### `/occupations/[code]` 一个职业

1. 数字 + 与中位对比
2. 100 格
3. **哪些任务**——逐条，标明被什么触及、第几阶；未触及的同样列出
4. **什么挡着**——闸门内联
5. 回到所属组

### `/updates` 最近

1. 这段时间：多少条、其中多少条留下证据、记录起点
2. 时间流：每行 = 标题 · 发布方 · 日期 · 证明了什么 · **源头链接**

### `/about` 三段，不超过一屏

这是什么 / 怎么算的（三句）/ 去哪里核对（技术白皮书 · GitHub · 白皮书）

## 删除与降级

| 路由 | 处置 | 理由 |
| --- | --- | --- |
| `/check` | 删 | 一句话，并入 `/about` |
| `/domains`、`/domains/[slug]` | 删 | 历史原型 20 赛道，与赛道轴重叠 |

### 一条规则

> **研究实体有详情页，没有索引页。**

能力和闸门是内部概念。读者不会想「浏览一下能力清单」，他是在看自己的职业时
想知道「『信息综合』指什么」。领域、职业、更新是会被浏览的，它们有索引。
