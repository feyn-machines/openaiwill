# 深度规划：把站点重建在赛道上

状态：规划，待评审
日期：2026-09-22
取代：本目录下 2026-09-22 的两份 v1／v2 规范中的产品结构部分。
设计系统迁移（字体、颜色、深色画布、方格组件）已落地，继续有效。

## 一、诊断

不是页面不好看的问题。有三层，一层比一层深。

### 1.1 站点建在错误的轴上

产品面向创业者，站点却建在 **O*NET 职业**上。创业者不会想「我是个法务助理」，
他想「我在做法律服务」。

更糟的是：**站内并存四套赛道词表，而站点用的是最差的一套。**

| # | 词表 | 规模 | 现状 |
| --- | --- | --- | --- |
| 1 | a16z 九大行业 | 9 | CLAUDE.md 要求保留、来源可溯，**站上零使用** |
| 2 | 本体 `market_group` / `market` | 40 组 / 265 赛道，中英齐全 | **站上零使用** |
| 3 | `src/content/markets.json` | 20 个编辑赛道 / 6 组 | 历史原型，`/domains` 渲染的就是它 |
| 4 | a16z 50 产品榜 + 9 应用标签 | 50 | 文档明令不得与行业目录混用 |

而且真正的目录（#2）**目前算不出进度**：

```
市场组 40 → 赛道 265 → 工作 614     每个赛道仅 2–5 个工作节点，中位 2
职业组 23 → 职业 1016 → 任务 18,838
两侧工作节点重叠 = 0
```

赛道那一侧是个**骨架**：265 个赛道共 614 个工作节点，且与职业侧完全不相交。
按 2 个工作节点算出来的百分比没有意义。这是本规划要解决的第一个问题。

### 1.2 品牌是我编的

DESIGN.md 第 9 行确认：主标题中文建议为「**AI 会让你的创业想法失去价值吗？**」

我写进代码的是「**AI 会杀死你的想法吗？**」——不是那句，丢掉了「创业」，
把「失去价值」换成了更像标题党的「杀死」。这是我自作主张改的，应当改回。

其次，品牌**只在首页出现一次**，其余页面是数据库标题。

### 1.3 每一页都在教概念，不是在回答问题

六个页面的 H1 与引导段，全部实测：

| 页面 | H1 | 引导段做的事 |
| --- | --- | --- |
| `/` | AI 会杀死你的想法吗？ | 品牌句 |
| `/capabilities` | 能力 | 定义「能力」这个词 |
| `/occupations` | 职业 | 定义「触及」并声明它不是结论 |
| `/gates` | 闸门 | 定义「闸门」，89 字 |
| `/updates` | AI 更新 | 定义「事件」并声明它不是判断 |
| `/method` | 方法与覆盖面 | 定义本页是什么 |

**五个页面的第一句话都在定义一个研究对象，紧接着是一句限定。**
读者要读完 50–90 字的概念教学，才能看到第一个数字。

这就是「AI 感」的来源——它不是文风问题，是**取向**问题：
站点在展示「我们研究了什么」，不是「你该知道什么」。

## 二、根本症结

把三层问题合起来看，只有一句话：

> **这个站点是为作者写的，不是为读者写的。**

轴按研究方便选（O*NET 齐全好用），页面按研究对象命名（能力／职业／闸门），
文案按研究严谨度写（先定义、再限定、最后数据），品牌按作者语感改。

每一条单独看都说得通，合起来就是「总体没有意义」。

## 三、赛道轴怎么建

这是整个规划的核心。三条路，代价与可信度都不同。

### 路线 A：补全赛道→工作目录

为 265 个赛道各自分解出真实的工作清单，从 2 个补到几十个。

- **代价**：这是一次完整的编目工程，工作量等同于重做一遍 O*NET 的任务分解。
- **风险**：自造的工作分类没有外部来源可溯，与 CLAUDE.md「来源可追溯为先」冲突。
- **结论**：不走。

### 路线 B：建「赛道 ↔ 职业」桥（推荐）

不重造工作目录，而是回答一个判断题：**这个职业是否在这个赛道里干活。**
建成之后，赛道的工作 = 它所含职业的任务之并集，直接继承已有的 18,838 个任务
和已经跑完的全部能力边。

**为什么可行**：这与站内已经跑过三轮的判断任务是同一形状——
给出两个受控词表里的条目，判是否成立，带 method/status/rationale 落库。
不需要新机制，只需要新的判断任务类型。

**规模与成本**：

| 做法 | 判断次数 | 参照 |
| --- | --- | --- |
| 赛道 × 职业 全量 | 265 × 1,016 = 269,240 | 闸门全量扫描是 189,607 次，约 100 分钟 |
| 赛道 × 职业组（先粗后细） | 265 × 23 = 6,095 | 几分钟 |

**建议先跑粗的 6,095 次**，得到「赛道 → 职业组」的映射，验证口径是否成立
（例如「法律服务」是否干净地落到「法律」职业组），再决定是否值得跑全量细化。

**必须一起定的三件事**：

1. **一个职业可以属于多个赛道**（会计师既在会计赛道也在制造业）。
   因此赛道的任务集合会重叠，**跨赛道的数字不可相加**，页面必须写明。
2. **需要一条新的边类型**（如 `serves_market`），进语义层受控词表，
   带 method/status，与现有边同样是 `ai_proposed` + `candidate`。
3. **赛道自己的 614 个工作节点不丢弃**，它们是另一套来源，
   与继承来的任务分开标注，不混算。

### 路线 C：赛道只做定性

赛道页不给百分比，只回答「这个赛道最近发生了什么」——把更新按赛道归类展示。

- **代价**：放弃了赛道级进度，而进度正是产品的核心对象。
- **价值**：零数据工作即可上线，可作为路线 B 完成前的过渡。

### 结论

**B 为主，C 作为 B 完成前的过渡形态。** 先跑 6,095 次粗判验证，
通过则细化，不通过就退回 C 并把原因写在方法页上。

### 四套词表怎么收敛

| 词表 | 处置 |
| --- | --- |
| 本体 40 组 / 265 赛道 | **唯一的产品赛道轴**，路线 B 挂在它上面 |
| a16z 九大行业 | 保留为**来源参照**，在方法页呈现，不作导航轴；它是一张图的口径，不是全球行业标准 |
| `markets.json` 20 个编辑赛道 | **下线**。它是原型，与本体目录语义重叠，留着就是第二个真相 |
| a16z 50 产品榜 | 保留在数据集中，仅作产品发现来源，不进赛道轴 |

## 四、解释搬去哪里

**已定（2026-09-22，用户确认）：页面上不做解释。方法、细节、限定全部搬到
技术白皮书与 GitHub。**

这条解决了前两版一直没解决的矛盾。我此前的做法是把"我们有多不确定"搬到页面正面，
结果是每页都在自证，读者拿不到东西。正确的做法是研究型产品的通行做法：

> **可信度由白皮书和开源仓库承担，不由每一个页面反复声明。**

### 4.1 三层分工

| 层 | 放什么 | 在哪里 |
| --- | --- | --- |
| **产品页** | 发现。一个数字、一句话说明它意味着什么、一行限定、一个链接 | 站点 |
| **技术白皮书** | 口径、判据、阶段定义、判断者对照、覆盖面、已知缺口 | 新文档，站点提供入口 |
| **源码与数据** | 全部可核对的东西：SQL、prompt、语义层、迁移、快照 | GitHub |

产品页上**一屏最多一句限定**，后面跟「方法 →」与「源码 →」两个链接。
其余全部下沉。

### 4.2 技术白皮书：组装，不是新写

站内已有 21 份技术文档，其中直接可用的：

- `docs/data/takeover-progress-framework-v1.md`
- `docs/data/ai-progress-knowledge-graph-v1.md`
- `docs/data/model-and-storage-boundary.md`
- `docs/data/semantic-layer-journal.md`（16 条方法修正）
- `docs/development/local-data-pipeline.md`

技术白皮书的工作是**编排与补缺**：给一条主线、补上当前 `/method` 页上那些
只存在于页面的内容（证据层级、三道封顶、宽度规则、判断者不对称），
然后把页面上的那些段落删掉。

与现有的 `docs/whitepaper.md` 分工明确：
那份是**公开白皮书**（这是什么倡议、为什么做），面向所有人；
技术白皮书面向想核对数字的人。两份都双语。

### 4.3 GitHub：今天指过去是个空壳

`github.com/feyn-machines/openaiwill` **当前只有 19 个跟踪文件**——
`datasets/`、`db/`、`docs/`、数据管线脚本、语义层全部未跟踪。

所以"放 GitHub 即可"本身是一项工作：

1. 按 SECURITY.md 与 CLAUDE.md 的发布边界筛选可公开的部分；
2. 根 `data/`（运行库、日志、凭据）、`design/reference/` 第三方原件保持在本地；
3. 以 `pnpm security:check` 与 `pnpm security:staged` 作为提交闸门；
4. 提交后仓库才具备"可核对"这一属性，页面才有资格指向它。

**在仓库真正装上方法之前，页面不应承诺"源码可查"。**

## 五、品牌与语气

### 5.1 改回确认过的话

| | 现在（我改的） | 应为（DESIGN.md 确认） |
| --- | --- | --- |
| 中文主标题 | AI 会杀死你的想法吗？ | **AI 会让你的创业想法失去价值吗？** |
| 英文主标题 | Will AI Kill Your Idea? | 不变 |
| 副标题 | 每一次 AI 更新，都可能改变你的创业判断。 | 不变 |

规则：**品牌文案不由实现者改写。** 需要改时改 DESIGN.md 并标注确认人与日期。

### 5.2 品牌要在每页在场

现在只有首页有主张，其余是数据库标题。每页顶部的那句话应当是**读者的问题**，
不是研究对象的名字（见第六节）。

### 5.3 语气：三条硬规则

1. **第一句话必须是一个发现，不能是一个定义。**
   术语第一次被用到时给一行解释，或者不给——它在技术白皮书里。
2. **一屏之内最多一句限定**，且必须具体。
   「阶段 4 为 0」可以；「请谨慎解读」不可以。
3. **正文不出现字段名**（`limiting_factor`、`evidence_standard`、`work_nodes_judged`）。
   那是研究者的词，属于技术白皮书。

## 六、逐页重做

页面按**读者的问题**命名，不按研究对象命名。

| 现在 | 重做后 | 第一句话（示意） |
| --- | --- | --- |
| `/` AI 会杀死你的想法吗？ | 不变（改回确认文案） | 这 100 格里，AI 已经摸到 81 格 |
| **（新）** `/markets` | **AI 走到你的赛道了吗** | 40 个赛道，按 AI 走进去的程度排 |
| **（新）** `/markets/[id]` | **这个赛道 AI 到哪一步了** | 法律服务：这 N 项工作里 AI 摸到 M 项 |
| `/occupations` 职业 | **按职业查** | 降为赛道的下一层，不再是主入口 |
| `/updates` AI 更新 | **最近发生了什么** | 上周有 N 条更新，其中 M 条动了你关心的赛道 |
| `/capabilities` 能力 | **AI 具体会做什么** | 降为研究入口，移出主导航第一梯队 |
| `/gates` 闸门 | **哪些事 AI 还接不了** | 同上 |
| `/method` 方法与覆盖面 | **降为一页入口** | 三句话说清这些数字怎么来的，然后是技术白皮书与 GitHub 两个链接 |

`/method` 现在有十节内容，重做后**不再承载方法本身**——它是入口，
方法在技术白皮书里，可核对的东西在仓库里。

导航从六项收到四项：**赛道 · 最近变化 · 方法 · 白皮书**。
职业、能力、闸门从赛道页进入。

### 首页的三段

1. 主张（确认文案，不加数据）
2. 100 格 + 一句发现 + 一行限定
3. 两个入口：**选你的赛道** / 看最近变化

「找到你的职业」不再是首页入口——那是第二层。

## 八、这版规划自己的风险

1. **赛道 ↔ 职业是判断，不是事实。** 它会和其他边一样是 `ai_proposed` + `candidate`。
   赛道页的数字因此继承了全部既有不确定性，再叠一层映射的不确定性。
   这一点必须在赛道页写明一次，不是回避的理由，但也不能假装没有。
2. **跨赛道数字不可相加**（职业可属多赛道）。页面若出现「全赛道合计」就是错的。
3. **粗判可能不通过。** 如果「赛道 → 职业组」的映射出现大面积一对多且无法收敛，
   说明这两套词表的粒度不匹配，那时应当退回路线 C 而不是硬上。
